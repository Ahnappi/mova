# mova

局域网内 **Windows ↔ macOS 直连互传** 的桌面应用：发文字、发文件，文件只在两台设备之间传输，不经服务器、不上架应用商店。

- 同一局域网内自动发现设备，也支持手动输入 `IP:端口` 直连；
- 文字即时互发；
- 文件（图片 / 视频 / PDF / Office 文档）拖拽或选择即发，收发双方都能看到实时进度、速度与预计剩余时间；
- 收完可以在应用内直接预览（图片 / 视频 / PDF），也可以一键在 Finder / 资源管理器里定位；
- 每次连接都会留下一条记录，能看到当时聊了什么、文件存在哪里，重启应用也不丢。

## 支持范围

| 项目 | 说明 |
| --- | --- |
| 平台 | macOS（Apple Silicon / Intel）、Windows 10 及以上 |
| 网络 | 同一局域网（UDP 广播发现 + TCP 直连），不需要外网 |
| 文件类型 | 图片 / 视频 / PDF / Office 文档，约 110 种视频格式，清单见 `lib/config/app_config.dart` |
| 文件大小 | 不设上限，按 4 MiB 分块流式读写，内存占用与文件大小无关 |
| 并发 | **一次只连接一台设备**（见下文「会话规则」） |

## 快速开始

```bash
flutter pub get
flutter run -d macos        # 或 -d windows
```

打包与检查：

```bash
flutter build macos --release     # 只能在 macOS 上执行
flutter build windows --release   # 只能在 Windows 上执行（release 不能交叉编译）
```

## 目录结构（分层）

```
lib/
├── config/           常量与依赖装配（AppConfig / buildProviders）
├── domain/models/    纯 Dart 领域模型（消息、会话、传输任务…）
├── data/
│   ├── repositories/   Repository：抽象 + 本地实现，负责业务规则
│   └── services/       Service：网络、文件、系统能力（不掺业务规则）
├── ui/
│   ├── chat/          首页：顶栏 / 设备发现 / 时间线 / 输入区 + ViewModel
│   ├── transfer/      文件卡片、发送确认框与传输 ViewModel
│   ├── history/       连接记录抽屉
│   ├── settings/      设置弹窗（设备名 / 保留期限 / 发送确认）
│   ├── preview/       应用内预览（图片 / 视频 / PDF）
│   └── theme/         设计系统与动效
└── utils/             Result（显式成败）、格式化、CRC32
```

调用链固定为 **View → ViewModel → Repository → Service**：

- View 只做展示与交互，不直接碰网络或文件；
- ViewModel 用 `ChangeNotifier` 持有界面状态，操作结果用 `Result<T>` 表达（`Ok` / `Error` 两个子类，强制调用方处理成败）；
- Repository 决定「什么时候算完成、什么时候算失败、要不要重试」；
- Service 只回答「能不能连上、能不能写进去、写到哪」。

文件读写一律在 Service 层（`FileStorageService` / `IncomingFileWriter`），Repository 不直接操作 `RandomAccessFile`。

## 协议

TCP 端口 **49153**，UDP 发现端口 **49154**。控制消息与文件数据共用一条 TCP 连接，采用二进制分帧：

```
| magic 'MOVA' (4B) | version (1B) | type (1B) | length (4B, 大端) | payload |
```

控制帧的 payload 是 UTF-8 JSON；文件块帧的 payload 是 `fileId (4B) + 原始数据`。

| type | 名称 | 方向 | 说明 |
| --- | --- | --- | --- |
| 1 | hello | 双向 | 互报名字与协议版本 |
| 2 | text | 双向 | 文本消息 |
| 3 | fileOffer | 发送 → 接收 | 请求发送（id / 名字 / 大小） |
| 4 | fileAccept | 接收 → 发送 | 同意接收 |
| 5 | fileReject | 接收 → 发送 | 拒绝接收 |
| 6 | fileChunk | 发送 → 接收 | 文件数据块 |
| 7 | fileEnd | 发送 → 接收 | 声明发完，带 `size` 与可选 `crc` |
| 8 | fileCancel | 双向 | 取消 |
| 9 | fileDone | 接收 → 发送 | **收尾回执**（`ok` + 失败原因） |

### 收尾握手（为什么要 9 号帧）

「数据推完了」不等于「对方收到了完整文件」。完整流程是：

1. 发送端推完最后一块，发 `fileEnd(size, crc)`；
2. 接收端核对实际字节数与 CRC32（校验在后台 isolate 里算，不占界面线程）；
3. 核对通过才把临时文件（`*.mova-part`）提交成正式文件（原子、不覆盖）；
4. 提交成功后发 `fileDone(ok:true)`；
5. 发送端收到 `ok:true` 才把任务标记为「已完成」。

任一步失败都会回 `fileDone(ok:false)`，发送端显示失败，接收端删掉半成品。对端协议版本低于 2（不认识回执帧）时，发送端不空等回执，直接按完成处理。

三个大小必须一致才算成功：**请求时声明的 `size`**、**结束帧声明的 `size`**、**实际落盘字节数**。只比后两个是不够的——源文件在传输途中被截短时，发送端会如实把截短后的大小写进结束帧，两端一核对反而「一致」；因此发送端在推流结束时也要比对「实际读出量 vs 请求时声明量」，不一致直接判失败。

## 可靠性设计

- **超时分两类**：等对方点「接收 / 拒绝」用 `offerResponseTimeout`（120s），且只对**已经发出请求**的任务计时，还在发送队列里排队的不会被误判；传输过程中只有「字节数长时间不动」才算卡住，用 `transferStallTimeout`（90s）。正常传大文件再久也不会被误判成「对方未响应」。
- **取消不会「诈尸」**：取消已发出的请求时会通知对端撤销；对端迟到的「接收」会被拒绝并回一条取消，已终结的任务不会被重新启动。发送循环在**最后一次 flush（等网络排空）之后**还会再核对一次取消，发送操作返回后也会统一复核「会话没换 + 任务仍在传输 + 没有取消请求」，否则绝不发结束帧——不会出现「最后一块已发出，取消就失效」。
- **终结状态不会被改写**：推流、收尾、回执、超时看护都跨 await，晚到的结果一律重新核对；任务若已被取消 / 超时 / 断连终结，后续异步结果只作废，不会把状态改回 `confirming` 或「已完成」。
- **接收准备可撤销**：点「接收」后要先选目录、探测写权限、建临时文件，这几步都跨 await，期间任务处于 `preparing`——重复点击会被挡回（不会两次占用同一个任务），异步返回后逐项核对会话与任务归属，失效就清理本次建的临时文件。
- **提交（改名）有明确边界**：临时文件改名是文件正式出现的那一步。提交前可以取消（临时文件被删、改名自然失败）；提交中与取消串行（取消先等改名落地，再把正式文件一起删掉）；提交后仍会复核一次，若期间已取消/断连/切会话，就按「取消优先」删除文件，且**不会**向发送端报告保存成功。
- **接收路径不外逃**：文件名来自对端，先清洗（去掉目录成分、`..`、控制字符、Windows 保留名、结尾的点），再规范化，并二次确认目标仍落在用户选择的保存目录内。
- **正式文件也不覆盖**：提交由操作系统用**一次原子调用**（硬链接：POSIX `link` / Windows `CreateHardLink`）完成「检查 + 创建」——目标已存在必定失败，且不会动那个文件，随后换一个名字重试。「先检查在不在、再改名」「先独占占位、再改名」都挡不住这两个步骤之间的窗口（占位之后那条路径照样可能被别人替换，而「目标现在是 0 字节」证明不了它属于本次接收），因此不覆盖的保证只能放在这一次原子调用里；拿不到这个能力（exFAT/FAT 等不支持硬链接的文件系统）就**明确失败**并在开始接收前就提示换目录，绝不退回会覆盖已有文件的普通改名。
- **接收用临时文件**：每次接收生成独立的 `*.mova-part`（时间戳 + 随机数）并以独占方式创建，绝不覆盖目录里已有的文件；核对通过才提交，半成品不会被当成完整文件打开。
- **会话规则**：已连接时第三方连入会被拒绝并弹出提示，当前会话不受影响；换会话会清空上一次的消息与传输任务，协议解析缓冲也随之复位。发送操作还额外绑定**发起时的 socket 与会话**：传大文件时若中途与 A 断开、随后连上 B，旧发送循环剩下的字节与结束帧都不会落到 B 上。连接尝试同样有归属：`isBusy` 把「正在连接」也算作占用，每次尝试带一个令牌，只有当前尝试能改动连接状态——连 A 久久不回、期间 B 已经连进来建好会话（或已经改连 C、新尝试还在半路）时，A 随后超时既不会接管连接，也不会广播 `disconnected`。
- **清理只认捕获到的路径**：作废一次接收时删哪些文件一律以这次接收自己记下的临时路径 / 正式路径为准，不回头查任务表——换会话会清空任务表，若按任务表判断「还删不删」，旧会话那几个 GB 的 `.mova-part` 就会被留在用户目录里。
- **背压**：发送端每积累 32 MiB 就等 socket 真正写出；接收端待落盘数据超过阈值就暂停读 socket，让 TCP 窗口压住对端，内存占用始终有界。
- **长文本按编码后的字节数判断**：单条消息上限 64 KiB，按 **UTF-8 编码后**的字节算（中文 3 字节/字，引号、反斜杠、换行还会被 JSON 转义放大），超了就返回一句能直接显示的错误，**不抛异常**；界面只有确认发出去了才清空输入框——否则粘一大段发不出去、输入还被清空，用户体验最差。
- **帧头声明的长度不可信**：帧头里的长度是**对端**填的，解析器在「等数据凑齐」**之前**就按类型校验上限（控制帧 64 KiB，文件块为块大小的两倍），版本不符、文件块过短同样立即判为协议错误并断开连接。否则一个「声明数 GB 的帧」会让缓冲一路扩容，而写盘队列的背压此刻完全够不着——字节还没解析成帧，根本进不了那个队列。解析缓冲本身也另有上界兜底。
- **落盘在后台 isolate**：写盘与 CRC32 都在独立 isolate 里做，界面只做「收帧 → 转发 → 更新进度」；起不了 isolate 时自动退化为异步写（功能不变）。
- **界面只重画该重画的部分**：进度每秒刷新十次，但只有对应那张文件卡会重建（按 id 订阅），整条时间线不会被带着重画。
- **历史写入可恢复**：写盘失败会保留「待保存」标记并按 1s → 2s → 4s（上限 30s）退避重试，且写入串行化不会互相覆盖；条数超过上限时淘汰最旧的记录。
- **退出是同一条队列上的最后一次写**：关闭时先停定时器与重试，再等已在跑的写入落地，最后才写最终快照——收尾写绕开队列直接落盘会和正在跑的写入抢同一个 `history.json.tmp`，而且旧快照**后**落盘会把更新的记录盖掉。补不补写看的是快照版本号而不是「待保存」标记（后者只表示变更已提交到队列，不代表已落盘）；关闭之后失败回调也不再安排重试。
- **收尾写是异步的，不再同步直写**：同步写的原意是「宿主不 await dispose 也能落盘」，但它会把主 isolate 整块占住——编码、写文件、改名期间界面动不了，**退出流程的超时计时器也走不动**，5 秒超时形同虚设，「重试／放弃」对话框根本弹不出来。现在退出流程（AppShutdown）会 await 收尾写，同步写不再是必需的，收尾写因此回到同一条异步队列。规模超过 `AppConfig.historyBackgroundEncodeEntries` 的快照，JSON 编码还会搬到后台 isolate（起不了 isolate 时自动退回主 isolate，绝不因此写不出去）。重试时先接着等那次还没结束的写入，不会与它重叠。
- **退出有统一的收尾流程**：光有「最后一次同步写」还不够——Provider 的 `dispose` 回调是同步的，宿主不 await，保存还没开始进程就可能结束。因此真正的退出走 `AppShutdown`：**封存连接层（关监听）** → 结束会话 → 收尾传输 → **等**连接记录落盘 → 才放行退出（幂等，每一步都有超时，不会把用户卡住）。窗口关闭由 `window_manager` 拦截：**Windows 上关窗口不会通知 Dart**，必须靠它；macOS / Linux 的系统级退出请求另由 `didRequestAppExit` 兜住；切到后台只是尽快落盘，不会结束会话。
- **退出第一步封存连接，而不是只断连**：`disconnect()` 会保留监听，退出期间（保存那几秒）另一台设备仍能连进来建新会话，而此刻传输仓储已在释放、历史仓储可能已关闭。所以收尾用的是 `seal()`：监听一起关掉，之后的 `connect` / `startListening` / `send` / 发文件一律拒绝，晚到的入站连接也会被直接关掉。
- **超时不等于保存完成，写失败更不能当成功**：`Future.timeout()` 只是不等了，并不会停掉原来的写入；而收尾那次同步写一旦失败（磁盘满 / 没权限 / 文件被占用），**异常必须一路抛上去**——吞掉它的话 `dispose()` 正常返回，退出流程就会把「没写出去」当成「已保存」直接退。两种情况都返回 `ExitBlocked`（提示语不同：「还在写」让人等，「写坏了」让人腾空间），**保留窗口**（不销毁）、弹窗让用户选「重试保存」或「放弃并退出」，系统级退出请求则返回 `cancel`。此时 `HistoryRepository.dispose()` 可以重复进入，重试会真的再等一次写入、再补一次快照，不会变成空操作。
- **两个退出入口共用一条确认流程**：关闭按钮与系统退出请求可能同时到来，用户还会连点关闭。整个「保存 → 受阻则询问 → 重试 → 放行」共用一个进行中的 Future，放行（解除拦截 + 销毁窗口）只做一次——否则会弹出两个互相冲突的对话框，或把窗口销毁多次。没放行时清掉缓存的结果，用户再点一次关闭还能重跑一遍。
- **窗口操作是可注入的接口**：`WindowController` 把 `setPreventClose` / `destroy` / 监听注册收在一处，真实实现转调 `window_manager`，测试注入替身。否则 Widget 测试没有原生插件实现，`setPreventClose` 的 `MissingPluginException` 会消失在未等待的 Future 里，测试既看不到也覆盖不到「关窗口走了退出流程」这条入口。
- **发现适应多网卡**：跳过 VPN / 虚拟机 / 容器网卡，按「私有网段 + 常见物理网卡」排序，广播目标定期随网络变化刷新，不再假定一定是 /24。
- **发送文件前先确认**：选完文件（或把文件拖进窗口）都会先弹一次确认，列出文件名、大小与接收方，点了「发送」才真的发出去——这是唯一一句「你确定吗」。可以在设置里关掉，给追求速度的人留一条捷径。两个入口共用同一段流程，不会出现「拖文件不用确认」这种例外。
- **失败的任务可以直接重发**：只对自己发出去且失败的文件给「重新发送」按钮（接收失败时文件在对方手里，重发无从谈起）。重发用**新的任务 id**（id 是双端认这一条传输的键，复用会让两条流程互相覆盖）、**重新 stat 源文件**（期间文件可能被移走或改过，拿旧大小去发会被再次判成「文件不一致」），并且要求会话仍是原来那一条——把文件发给别的设备是不可以的。旧的失败卡片会被新卡片替换，连接记录里那条失败仍然保留。
- **连接记录按保留期限清理**：设置里可选 1/7/30/90/365 天或永久保留。载入记录时先筛一遍，改短期限也会立刻清理并告诉用户清了几条。当前正在进行的会话**永远不清理**（它还在被写入）；已接收到的文件不受影响。条数上限（`maxHistorySessions`）仍然生效：这两个约束一个管时间、一个管体量。
- **设备名可以在设置里改**：默认是主机名，改完立刻反映到下一拍 UDP 心跳上（正在搜索时会重启一次发现），对方不用等到重启应用；已建立的连接不会改（hello 帧只在建连时发一次）。

## 已知限制

- 不支持断点续传、端到端加密、代码签名与公证（未上架，内网自用）；
- 一次只连接一台设备，不支持多设备同时会话；
- 单条文本消息上限 64 KiB（编码后），更长的请分几条发；
- 发现依赖 UDP 广播，跨网段或严格隔离的网络请改用手动 IP 直连；
- 历史记录是整份 JSON 覆盖写，条数上限 200；若日后需要长期保存全部记录，应换成追加式日志或本地数据库。
- 保存位置必须支持硬链接（提交正式文件用的原子操作）：NTFS / APFS / ext4 等都没问题，**exFAT、FAT32 及部分网络盘不支持**。应用会在开始接收前探测并提示换目录；实机验收请把「保存到 exFAT 的 U 盘 / 移动硬盘」列为一个必测项，确认拿到的是明确的提示而不是传完才失败。Windows 侧的 `CreateHardLinkW` 路径需要在 Windows 真机上验证。
